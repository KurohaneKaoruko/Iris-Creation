# v0.1.1-rc.3 可用性验收

## 结论

内测候选版，不是稳定版。旧 rc.1/rc.2 标签保留且没有公开 Release；rc.3 的 GitHub Actions 结果是跨平台构建依据。自动通过不等于真实设备验收完成。

## 门禁

- 主 CI：统一版本检查、Node 发布安全测试、295 项前端测试/类型检查/构建、完整 Rust 测试和本机模拟 Provider RPC/WS 验收。
- Windows/macOS/Linux 每个矩阵任务：构建对应 Tauri 包、构建实际后端服务、隔离临时数据并运行模拟 AI 的文件保存/冲突/历史恢复/停止/错误/重启验收。
- 不在三平台重复运行整个 Rust 测试套件：rc.1 与 rc.2 的该附加步骤均在公开页面显示 exit 101，详细 runner 日志不可匿名读取；主 CI 完整套件成功。该门禁被移除是为了避免未诊断的重复步骤错误阻断真正的目标构建。目标平台编译和真实服务验收仍是硬门禁。
- 发布前校验本版本五个预期平台安装包名称、零字节、数量、SHA256SUMS 和 GitHub 返回的上传尺寸/digest。仅在全数相符后公开。
- 已有 Release/草稿不删除、不覆盖。上传失败会保留草稿，要求人工检查。
- RPM 不接受带连字符的 SemVer 预发布号。Linux 候选版先用完整候选版本构建应用和 DEB/AppImage，再将 RPM 包元数据编码为基础版本 + `0.<预发布标识>` release；RPM 的 `0.*` 低于正式发布的 `1`，候选二进制本身仍为 `-rc.N` 版本。实机上的 RPM 升级行为仍需人工验收。
- AppImage 依赖的上游 `linuxdeploy` 外部二进制在当前本地网络以约 30 KB/s 下载，完整 19 MB 文件无法在 3 分钟下载时限内获得；这项本地网络限制不等于 Tauri 打包逻辑失败。GitHub Actions 使用其 runner 网络独立执行 AppImage 构建，仍以该 job 结果作为发布门禁。

## 自动化覆盖的核心场景

生产前端和本机服务启动；Unicode/CRLF 章节保存；过期基线保护；版本历史读取与恢复；作品导出；路径越界拒绝；模拟 Provider 流式生成、取消、缺密钥、401、损坏 JSON、断线；强制结束服务后重启读回设置、会话和作品副本。
